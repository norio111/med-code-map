# 設計ノート

## 目的

レセプト電算マスターを、区分番号・レセ電コード・国際分類を別軸として保持できる形へ構造化する。FHIRやICFへ一つに統合することではなく、それぞれの体系を保持したまま参照関係を作ることを目的とする。

## 中心となる判断

### 1. コードと区分番号を分ける

点数表区分番号（例：`H001`）と9桁の診療行為コードは識別単位が異なる。両者を同じ主キーへ押し込まず、`code_kubun_map`を介して対応させる。

### 2. 対応関係に改定を持たせる

対応関係は制度改定に依存するため、`code_kubun_map`へ`revision_id`を持たせる。v0.3では`code_item`自体も複数版を併存できる。

### 3. 点数は改定に属させる

同じ診療行為コードでも、点数は改定で変わる。`code_item`の識別子を`(cs_id, code)`のままにすると、新しい版を入れた時点で古い点数が消える。v0.3で`revision_id`を識別子へ加え、同じコードが改定ごとに別の行を持つようにした。

これは「統合せず、それぞれの粒度を保つ」という本リポジトリの方針を、時間軸へ適用したもの。上書きすれば最新の状態は常に正しいが、何がどう変わったかは引けなくなる。2年ごとの改定があり、改定前の請求を後から確認する場面がある領域では、変わったという事実のほうが情報量が大きいと判断した。

この判断は令和8年度版を取り込んだ時点で検証できた。同一コードの属性変更と、コードの廃止・新設は、2版を保持していれば機械的に出せる。一方で、制度項目としての分割・統合は出せないことも同時に分かった。レセ電コードは制度項目そのものではなく、年度ごとの算定条件を表現する実装コードであり、制度項目を第三の軸として持つ必要がある。詳細は[`revision-diff-R06-R08.md`](revision-diff-R06-R08.md)。

### 4. 施設基準の枠位置を失わない

施設基準10枠は単なる集合ではない。枠の位置からグループが決まり、グループ内OR・グループ間ANDとして評価されるため、`group_no`と`slot_no`を保存する。

### 5. 欠損を推測で埋めない

移行先が存在しない旧傷病名は`NULL`として保存する。名称の手入力値には検証状態を持たせ、元データと同じ確度として扱わない。

### 6. 既知件数を回帰テストとして使う

件数一致は項番の意味を証明しないが、同じ入力から同じ結果を再現できるかを検査できる。意味は公式仕様との照合、再現性は期待件数チェックという別の検証に分ける。

## 今後の再設計候補

2026-09-15：制度項目の第三の軸は、まず公開用JSONの注釈として追加した。既存DBを変更せず、明示コード対応を介して機械抽出した属性を結合する。施設プロフィールはブラウザ内の一時的な選択として扱う。詳細は[`impact-design.md`](impact-design.md)。

- `dataset_release`を追加し、制度改定と各マスターの更新日を分離する
- `code_item`、`disease`へリリースIDを加え、複数時点を併存させる
- 修飾語と病名の組合せ制約を調査する
- 告示・通知・疑義解釈を、出典と適用期間付きで接続する
- 訪問看護療養費マスターを別コード体系として追加する
