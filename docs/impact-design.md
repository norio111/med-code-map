# 施設別の改定影響チェッカー MVP

## 完成した縦の範囲

`impact.html`で3疾患のⅠ・Ⅱ・Ⅲ（9区分）を個別・同時選択し、R06→R08の関連項目を表示する。各項目に年度別の記載、変更の種類、実務上の確認事項、主張単位の根拠リンク、コード明細がある。

9区分すべてを選ぶと8カード、各カード内に9つの区分別明細と判定を表示する。Ⅲ単独では総合計画評価料を除いた7カード。1つだけ選ぶとその区分の明細だけになる。共通の旧コードや総合計画評価料のコードは再掲するが、区分間のコード移行を意味しない。改定全体を網羅しない。

## 最小のデータモデル

SQLのテーブルは追加しない。既存DBを読取専用で参照し、制度の第三の軸は編集可能な`data/impact-catalog.json`に置く。JSONはDBの複製スキーマではなく、公開用の制度注釈である。

| 概念 | MVPでの保持場所・既存モデルとの関係 |
|---|---|
| facility_profile | ブラウザのチェック状態。氏名・施設名・患者情報・届出日を保存しない。既存`my_facility`とは同期しない |
| 施設選択肢 | `facilities`。`id`は疾患・等級の意味的ID。`rehab_type`、`grade`、`kubun_no`、表示名、根拠・確認状態を別項目で保持 |
| policy_item | 年度に依存しない`policy_items[].id`。疾患ごとの識別子は`variants[].id`（例：`early:disuse_i`） |
| policy_code_map | `variants[].code_map`。既存`code_item`の`(cs_id, code, revision_id)`を明示参照。所属の編集判断と抽出した属性を分ける |
| revision_change | `changes`。旧新年度は既存`revision`と同じR06/R08。種類・旧内容・新内容・確度・出典を主張ごとに持つ |
| evidence | `evidence`辞書。資料名、URL、場所、要旨、確認状態、確認日、人の確認記録、既存監査への参照 |

`policy_code_map`はコードの後継関係ではない。名称・点数が一致しても旧新を対応付けない。初期投入時のマスター検索で候補を絞り、区分・等級・制度内容を確認してコード集合を固定した。公開JSONの再生成には名称による所属推定を使わず、この明示リストだけを使う。制度分割の解釈は手入力のInterpretationである。

施設IDは`cerebrovascular_i/ii/iii`、`disuse_i/ii/iii`、`musculoskeletal_i/ii/iii`。従来の`H001-I`等から移行した（プロフィール保存機能はない）。区分番号は疾患別のH001・H001-2・H002であり、等級の識別には使わない。マスターの施設基準枠の一致から届出を同一視しない。特定患者・旧リ減は、区分番号と名称の最初の等級を照合して明示コード集合を固定し、エクスポート時も等級を検証する。後続の括弧番号や点数で旧新を対応付けない。

## 生成と配信

```text
指定年度の公式マスター
  → 既存 load_master.py --all → 2年度のSQLite（非公開）
編集した制度項目・明示コード対応・根拠（data/impact-catalog.json）
  ＋ SQLite の code_item / code_kubun_map / code_quantity_rule / code_facility_req
  → src/export_impact.py → assets/impact-data.json（検証・参照用）
                       → assets/impact-data.js（同じデータのブラウザ読込用）
  → impact.html + assets/impact.js（ブラウザで絞込み）
```

GitHub PagesでHTML・CSS・JS・JSONを配信するだけで動く。公開サーバー処理、認証、外部JS依存、SQLite WASMは不要。選択をURL、ストレージ、外部APIへ送らない。ローカルのHTTPサーバーは開発プレビュー専用。

### HTTPとfile:///の共通初期化（2026-09-15修正）

旧実装ではJSONのfetch成功後にだけ選択肢を作成していた。Edgeのfile:///ではCORS制限によりfetchが失敗し、施設・改定の欄が空になった。HTTP経由では正常だった。

修正後は通常の外部scriptタグをdeferで、`impact-data.js`→`impact.js`の順に実行する。JSON fetchやモジュール読込を必要とせず、両経路で同じデータと初期化処理を使う。データJSはエクスポート結果をJSON文字列として安全にシリアライズし、`globalThis.MED_CODE_MAP_IMPACT_DATA`に設定する生成物。監査用の正本は引き続きカタログJSONであり、コード属性の機械抽出処理・判定・集計は変更しない。

HTMLには常時利用できる初期化未完了の案内と欄のプレースホルダーを置き、成功時だけ案内を隠す。HTML内の小さな監視処理が外部JSの欠落・構文エラーを検知し、操作JSはデータ形式を検証する。失敗時はボタンを無効化し、原因・ファイル配置・両方の起動方法を01の直下に表示する。file:///では実行エラーのファイル名がブラウザから取得できない場合があり、その場合は詳細を取得できない旨を表示する。JavaScript自体が無効でも静的な案内は残る。施設選択が0件の間は実行ボタンを無効にする。

起動方法：

1. フォルダ全体を展開して`impact.html`をダブルクリック（file:///）。assetsフォルダも必要。
2. リポジトリ直下で`py -m http.server 8000 --bind 127.0.0.1`を実行し、`http://localhost:8000/impact.html`を開く。

エクスポーターは両年度の全件取込が必要。H区分・単位系の件数と集合差が既知スナップショットと違う場合、根拠参照がない場合、コードが存在しない場合、区分が明示対応と異なる場合は出力前に停止する。既存DBは変更しない。公開JSONにはカタログSHA-256と元CSVのSHA-256を保持する。元CSVのハッシュは出典情報であり、任意DBの入力履歴を証明するものではない。

## 判定

| 区分 | 条件 |
|---|---|
| 対象 | 編集した直接対応があり、登録済みの追加確認条件がない。算定可という意味ではない |
| 条件付き | 対応があり、患者・実施条件等の確認が必要 |
| 対象外 | 当該選択範囲の外と明示登録されているもの。初期非表示 |
| 要確認 | 年度不一致・未登録の対応・不明の対応。データ欠落を対象外にしない |

判定表は下記の9区分拡張記録を参照。複数選択では未登録／要確認を優先し、全対応が対象外のときだけ対象外とする。対象外と条件付きの混在は条件付き。各区分の判定と理由を明細にも表示する。

対象外表示の例として、既存監査のリンパ浮腫複合的治療料（1以外）を1件登録する。これは9つの選択区分への直接対応がないという限定的な表示であり、その施設に影響がないとの断定ではない。

## 監査表現

- `origin=manual`：資料の要約、制度の同一性、施設との関係、明示コード集合。人による承認済みという意味ではない。
- `origin=machine`：DBの名称・点数・区分・施設基準枠・年度間の存在。制度分割の推定はしない。
- `epistemic`：Fact／Interpretation／Hypothesis。MVPにHypothesisの制度主張は含めない。
- `human_review=null`：人の最終確認を受けていない。今回のエージェントによる照合と、人の確認を混同しない。
- コード集合差はR06のみ／R08のみ、同一コードの点数変更は別フィールド。集計の「消滅・新設」も指定集合の差である。
- PDFの本文ページと通しページは別フィールド。個別改定項目の本文561ページはPDFの573ページへリンクする。通知の本文499ページはPDF通し499ページ。
- CSVはページを捏造せずコードと項番を位置情報にする。予定XLSXと仕様説明書は既存監査を再利用し、未再照合のページやセルへ推測リンクを付けない。

既存監査にない詳細条件を推測で加えない。今回確認した正式通知は、疾患別の関係を条件付きとする根拠に接続した。個別改定項目の提案段階の記載はその資料名・確認状態を維持しており、告示・通知・疑義解釈の全件照合済みとは扱わない。

## 結果カードの表示整理（2026-09-15）

正本JSONの`changes`、`checks`、`variants`、`evidence`、機械抽出結果と判定値は変更しない。通常画面は、制度項目名と判定、R06/R08の変更表、判定別の利用者向け説明、登録済みの実務確認事項、主な根拠リンクの順に示す。要確認では該当区分の未照合理由、総合計画評価料Ⅲの対象外では「当該届出単独」という限定理由も表示する。

各カードの「判定根拠・コード・監査情報を確認する」は初期状態で閉じる。中には判定方法、専門職による最終確認の集約表示、変更主張ごとのFact／Interpretation／Hypothesisと入力経路、区分ごとの判定・コード・マスター属性、主張単位の根拠ID、資料URL・ページ・確認状態を置く。区分の明細も初期状態で閉じる。監査用語は日本語の意味を先に表示する。同じURL・PDF通しページの根拠は監査欄で一つのリンクにまとめ、根拠IDごとの要旨と確認状態は残す。未登録のコードは専用文だけを示し、空リストを生成しない。

通常画面の主な根拠リンクは、制度変更の一次資料と選択区分の資料を優先して最大2件とする。全根拠は折りたたみ内の一覧で確認できる。`human_review`は主張・区分・資料を集約してカードごとに1回だけ表示し、別の確認記録がある場合はその値を示す。正本や生成データの確認状態は保持し、表示時に繰り返しの最終確認文だけを省く。算定可否の判定や制度解釈は追加していない。
